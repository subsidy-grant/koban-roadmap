# _tools — 掲載情報を機械で確かめる道具

サイトに載せている情報は、こちらの都合と関係なく古くなる。役所のページは告知なく
URLが変わり、様式は年度・公募回ごとに差し替わる。制度106件・様式743件を人手で追うのは
無理なので、ここに置いた2本で機械に見張らせる。

**どちらも「断定」はしない。**リンク切れは機械が判定できるが、「この様式が
この制度の最新版か」は人が公式ページを見ないと決められない。道具は人が見るべき
場所を絞るところまでをやる。

---

## check_links.py — リンク切れと『中身の差し替え』を見つける

```bash
python3 _tools/check_links.py                     # 全部（約880件・15〜20分）
python3 _tools/check_links.py --only city.fuchu   # URLに文字列を含むものだけ
python3 _tools/check_links.py --kind docs-file    # 様式ファイル743件だけ
python3 _tools/check_links.py --no-save           # 台帳を書き換えずに見るだけ
```

絞り込んだときは `link_report_part.md` に出す（全件版のレポートを潰さないため）。

見るもの：`index.html` の `PROGRAMS`＋`ADDED`（制度の公式ページ106件）、
`PROGRAM_DOCS`（様式743件・ポータル84件）、各HTMLの出典リンク。

**200が返るだけでは足りない。**同じURLのまま中身が差し替わることがあるので、
`Content-Length` と `Last-Modified` を前回値（`link_status.json`）と比べて
「差し替わった可能性」として出す。

### 誤検知を消すために入れてある条件（すべて 2026-07-31 に実測して決めた）

差し替え検出は**様式ファイル（PDF・Word・Excel）だけ**に効かせている。HTMLページは
中身が動くのが普通で、更新日時に取得時刻をそのまま返すCMSもある（`city.chichibu.lg.jp`）。
全ページを対象にすると毎週12件前後の「変化あり」が並び、本物のリンク切れが埋もれる。

- **ETagは使わない** — `mhlw.go.jp` は同じファイルでもリクエストごとにETagが変わる（Apacheのinode由来）
- **`Accept-Encoding: identity` を送る** — gzipで返るかが毎回変わるサーバーがあり（`chusho.meti.go.jp`）、そのままだとサイズが違って見える
- **`Content-Length: 0` は「不明」として捨てる** — HEADにだけ0を返すサーバーがある（`city.chichibu.lg.jp`）
- **取り方（HEAD/GET・エンコーディング）が前回と違うときは比べない**
- **更新日時は1日以上ずれたときだけ拾う** — 負荷分散でmtimeが違うサーバーに当たる。
  `jfc.go.jp` は1秒、八王子市は**2ファイルの更新日時が互いに入れ替わって**返ってきた（7分差）。
  中身が本当に差し替われば `Content-Length` が動くので、そちらを主に見る
- **URLを空白で切らない** — ファイル名に全角スペースを含むURLがある（港区の
  「第2号様式　誓約書兼同意書.docx」）。素朴に空白で切ると断片が毎週「リンク切れ」に
  なるので、正しく読めているURLの前半分でしかない候補は落とす

この条件を入れる前は全178件中12件が誤検知だった。入れたあと、同じ178件を続けて
2回確認して**変化あり0件**（2026-07-31 13:16 と 13:20 の実測）。

判定と終了コード：

| 判定 | 意味 | 終了コード |
|---|---|---|
| リンク切れ／**前は開けたのに開けなくなった**／ファイル種別の変化／移転／差し替え | 要対応 | 1 |
| 403・タイムアウト（前から開けていない） | 目視が要る | 2 |
| 変化なし・新規 | 対応不要 | 0 |

**404を返さないサーバーがある。**`it-shien.smrj.go.jp` は存在しないパスにも403を返す
（2026-07-31 実測）ので、404だけを見ているとそのホストのリンク切れを取り逃す。
そこで「いつも403のホスト」と「前は開けたのに開けなくなったURL」を区別し、
後者だけ要対応に上げる。1回きりの通信エラーで赤くしないよう、**2回続けて失敗**して
からにしている（連続失敗回数は台帳の `fail_streak`）。

判定規則は `python3 _tools/test_classify.py` で確かめられる（通信しない・12件）。
規則をいじるときは、先にここへ1件足すこと。

出力：`link_report.md`（全件）、`link_report_brief.md`（Issue用・正常分を省く）、
`link_status.json`（前回値の台帳）。

**UAについて。**`chusho.meti.go.jp` はWAFがあり、素性だけのUAには403を返す
（2026-07-31 実測）。ブラウザ相当の文字列にリポジトリURLを足した形にしてある。
アクセス解析のビーコン（goatcounter）は自分でページビューを作ってしまうので叩かない。

### 自動実行

`.github/workflows/linkcheck.yml` が毎週月曜09:00 JSTに回す（手動実行も可）。
要対応が出たら `linkcheck` ラベルのIssueに追記する（毎回新規に立てない）。
結果はリポジトリにコミットされるので、いつ何が変わったかはgit logで追える。

## build_docs.py — 様式を自動で拾って掲載する

```bash
python3 _tools/build_docs.py --pref kanagawa          # 下見（何が載るか出すだけ）
python3 _tools/build_docs.py --pref kanagawa --apply  # index.html に書き込む
python3 _tools/build_docs.py --all --apply            # 未掲載の全制度
python3 _tools/build_docs.py --pref tokyo --recheck   # 掲載済みと突き合わせて精度を見る
```

東京都20制度は人が1件ずつ公式ページを開いて掲載した。そのときやっていた判断を
規則にしたのがこれ。**判断を機械に移しただけで、基準は緩めていない。**
通らなかったものは載せずに `docs_build_report.md` の「目視送り」に出す。

### 実装している規則（どれも実際のページで踏んだ失敗から決めた）

| 規則 | きっかけになった実例 |
|---|---|
| 見出しが別の制度名を名乗っていたら配下を全部落とす | 杉並区のページに別制度（特例資金融資）と厚労省の熱中症資料が並んでいた |
| 段は**書類名から**決め、決まらないときだけ見出しを見る | 川崎市の「公募要領・交付要綱・申請書類」という1つの見出しに読みものと様式が同居。見出し優先だと交付申請書まで「読む」段に落ちた |
| 「読むもの」を先に判定 | 「申請の手引き」は名前に申請が入るが提出物ではない |
| 変更を実績より先に判定 | 「変更報告書」は報告の語を含むが提出は途中 |
| リンク文字が「ワード版：63KB」等なら、ファイル名→手前の文字の順に補う | 鎌倉市は書類名を別のセルに置いている |
| 手前の文字は「書・表・届・計画」等を含む塊だけ採る | 平塚市の「請求書の提出は実績報告後です」を名前にしてしまった |
| 同名が並ぶ／名前が短いときは見出しを頭に付ける | 平塚市に「事業計画書」が3つ（事前確認用・交付申請用・実績報告用） |
| 事例・過去年度・会社名つきは落とす | 江戸川区の「令和3年度」見出し配下の導入事例 |
| 種別とサイズは実測。拡張子と中身が食い違えば載せない | — |
| 交付申請の様式が1つも無い制度は載せない | — |

### 精度（2026-07-31 実測）

人が手で掲載した東京都20制度を正解として突き合わせた結果、
**20制度すべてを掲載・人が載せた131ファイルを100%拾えた**。
杉並区は自動でも正しく除外された。

この基準で関東6都県を回し、**84制度・743ファイル**を掲載、23制度を目視送りにした。

## collect_docs.py — 様式の候補を拾う（下書き作り）

```bash
python3 _tools/collect_docs.py               # 様式未掲載の制度すべて
python3 _tools/collect_docs.py --only tokyo_ # 制度キーで絞る
python3 _tools/collect_docs.py --head        # 候補にHEADを打ち種別・サイズも取る
```

制度の公式ページを開いてPDF・Word・Excelへのリンクを拾い、様式らしい語
（様式／申請書／交付申請／実績報告／記載例…）で並べ替えて
`docs_candidates.md` に出す。`--only` のときは別ファイルに書く。

**出力は掲載可能なリストではない。**同じページに別制度の様式や前年度のファイルが
並んでいることがあり、機械にはどれがどの制度のものか断定できない。
`PROGRAM_DOCS` は「公式サイトで実在を確認できたものだけ」という約束で作ってあるので、
人が公式ページを開いて確かめたものだけを入れること。

2026-07-31 時点：`build_docs.py` が **96制度・900ファイル**を掲載したので、
このスクリプトの担当は**残り11制度**（公式ページに様式が置かれていないもの）だけになった。
自動掲載の判定理由は `docs_build_report.md` の「目視送り」に、
拾えているファイルの一覧は `docs_candidates.md` にある。手で足すときはこの2つを見る。

**機械の候補をそのまま載せてはいけない実例**：杉並区のページに並んでいたPDFは、
デジタル化推進事業助成のものではなく別制度（特例資金融資）と厚労省の熱中症対策資料だった。
`build_docs.py` はこれを見出しから判定して除外するが、除外規則を通ったものが
必ず正しいとは限らない。**掲載後に一度は画面で見ること。**

## build_page_data.py — 書類作成ページ用のデータを作る

`documents.html`（申請書類の準備）と `program.html`（1ページ1制度の詳細ページ、
2026-08-05新設）は、制度名・締切・様式の一覧を使う。
これを両ページに書き写すと出所が3つになり、必ずどれかが古くなるので、
**index.html を唯一の出所として `page_data.js` を機械的に作る。**

```bash
python3 _tools/build_page_data.py          # 作り直す（変化が無ければ書かない）
python3 _tools/build_page_data.py --check  # 一致しているかだけ見る（終了コード1で不一致）
```

**正規表現ではなく実ブラウザ（Playwright）で読む。**index.html の制度データは
`var PROGRAMS = {...}` のあとに `var ADDED = {...}` が実行時にマージされる作りで、
テキストを読むだけでは最終形にならないため。JSエラーが出ていたら
マージ前の値を掴む恐れがあるので、その場合は生成せず止まる。

- `page_data.js` は**自動生成。手で編集しない。**
- **index.html の制度データや様式を触ったら流し直すこと。**忘れると書類作成ページ・制度詳細ページが古くなる。
- 毎週のリンク確認ワークフロー（`.github/workflows/linkcheck.yml`）でも作り直し、
  差分が出たらそのままコミットするので、忘れても翌週には直る。

2026-07-31 時点：制度107件・様式を載せている制度84件・様式ファイル743件／203KB。

### 制度ページと様式ページが別のとき（2026-07-31 に23制度を手作業で辿って分かったこと）

自動掲載できなかった23制度を1件ずつ辿ったところ、**様式が無いのではなく、
制度の説明ページとは別のページに置いてある**ものが大半だった。
そこで `FORM_PAGES`（build_docs.py）に「この制度の様式はこのURL」を書けるようにした。
書けば、以降の抽出・段分け・掲載判定はそのまま効く。

そのとき見つけて直したもの：

| 見つけたこと | 直したところ |
|---|---|
| リンク文字が全部「確認資料」「任意様式」で、書類名は見出しのほうにある（観光庁） | `GENERIC_LABEL` に当たるリンク文字は見出しを名前に使う |
| 「補助対象外リスト」が交付申請の段に入る | 読みものの語に `対象外` を追加 |
| 制度リンクが総合案内ページを指していた（東松山市・杉並区） | index.html の `link` を制度そのもののページへ差し替え |
| HEADに502を返しGETなら200というサーバー（TOKYO創業ステーション） | 計測はHEADが失敗してもGETまで試す（build_docs.py は元からそうなっていた） |
| 様式が一式ZIPで配られる（相模原市・TOKYO創業ステーション） | 種別 `ZIP` を追加し、色分けも別にした |

**それでも載せられなかった11制度**は、公式ページに様式ファイルが本当に置かれていない。
電子申請システム上で入力する方式、窓口での事前相談が先、実施主体が商工会、など理由は
`docs_build_report.md` の「目視送り」に1件ずつ書いてある。**書類が無いという意味ではない。**

## build_zipcode.py — 郵便番号から住所を出すためのデータ

書類作成ページ（documents.html）で、郵便番号を7桁入れると住所が入る。
**外部の郵便番号検索APIは使っていない。**同ページに「入力した内容は端末の中だけ」と
書いてあり、郵便番号を外に投げるとその約束が崩れるため。

```bash
python3 _tools/build_zipcode.py          # 日本郵便から取得して zipdata/ を作り直す
python3 _tools/build_zipcode.py --check  # いま入っている件数を数える
```

- 元データ：日本郵便の `utf_ken_all.zip`。
  **直リンクはUser-Agentによって404を返す**ので、実ブラウザ（Playwright）で取得している
- 出力：`zipdata/<上3桁>.json`。2026-07-31時点で **948ファイル・郵便番号120,682件・合計6.2MB**。
  1回の検索で落ちてくるのは1ファイルだけ（平均6.7KB）
- 町域欄の「以下に掲載がない場合」「◯◯の次に番地がくる場合」などの注記は住所ではないので落としている。
  落としきったら市区町村までで止める（申請書に注記が載るのを防ぐため）
- 同じ郵便番号に町域が複数あるものは先に出たほうを残す（3,831件）。
  どれが正しいかは機械では決められないので、画面では番地から先を本人に確認してもらう作りにしている
- **郵便番号は月1回更新される。**毎週のリンク確認ワークフローで作り直して差分をコミットする
