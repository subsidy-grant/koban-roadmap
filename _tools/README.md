# _tools — 掲載情報を機械で確かめる道具

サイトに載せている情報は、こちらの都合と関係なく古くなる。役所のページは告知なく
URLが変わり、様式は年度・公募回ごとに差し替わる。制度106件・様式37件を人手で追うのは
無理なので、ここに置いた2本で機械に見張らせる。

**どちらも「断定」はしない。**リンク切れは機械が判定できるが、「この様式が
この制度の最新版か」は人が公式ページを見ないと決められない。道具は人が見るべき
場所を絞るところまでをやる。

---

## check_links.py — リンク切れと『中身の差し替え』を見つける

```bash
python3 _tools/check_links.py                     # 全部（178件・3〜5分）
python3 _tools/check_links.py --only city.fuchu   # URLに文字列を含むものだけ
python3 _tools/check_links.py --kind docs-file    # 様式ファイル37件だけ
python3 _tools/check_links.py --no-save           # 台帳を書き換えずに見るだけ
```

絞り込んだときは `link_report_part.md` に出す（全件版のレポートを潰さないため）。

見るもの：`index.html` の `PROGRAMS`＋`ADDED`（制度の公式ページ106件）、
`PROGRAM_DOCS`（様式37件・ポータル6件）、各HTMLの出典リンク。

**200が返るだけでは足りない。**同じURLのまま中身が差し替わることがあるので、
`Content-Length` と `Last-Modified` を前回値（`link_status.json`）と比べて
「差し替わった可能性」として出す。

### 誤検知を消すために入れてある条件（すべて 2026-07-31 に実測して決めた）

差し替え検出は**様式ファイル（PDF・Word・Excel）だけ**に効かせている。HTMLページは
中身が動くのが普通で、更新日時に取得時刻をそのまま返すCMSもある（`city.chichibu.lg.jp`）。
全ページを対象にすると毎週12件前後の「変化あり」が並び、本物のリンク切れが埋もれる。

- **ETagは使わない** — `mhlw.go.jp` は同じファイルでもリクエストごとにETagが変わる（Apacheのinode由来）
- **`Accept-Encoding: identity` を送る** — gzipで返るかが毎回変わるサーバーがあり（`chusho.meti.go.jp`）、そのままだとサイズが違って見える
- **`Content-Length: 0` は「不明」として捨てる** — HEADにだけ0を返すサーバーがある（`city.chichibu.lg.jp`）
- **取り方（HEAD/GET・エンコーディング）が前回と違うときは比べない**
- **更新日時の60秒以内の差は無視** — 負荷分散で別サーバーに当たると1秒ずれる（`jfc.go.jp`）

この条件を入れる前は全178件中12件が誤検知だった。入れたあと、同じ178件を続けて
2回確認して**変化あり0件**（2026-07-31 13:16 と 13:20 の実測）。

判定と終了コード：

| 判定 | 意味 | 終了コード |
|---|---|---|
| リンク切れ／**前は開けたのに開けなくなった**／ファイル種別の変化／移転／差し替え | 要対応 | 1 |
| 403・タイムアウト（前から開けていない） | 目視が要る | 2 |
| 変化なし・新規 | 対応不要 | 0 |

**404を返さないサーバーがある。**`it-shien.smrj.go.jp` は存在しないパスにも403を返す
（2026-07-31 実測）ので、404だけを見ているとそのホストのリンク切れを取り逃す。
そこで「いつも403のホスト」と「前は開けたのに開けなくなったURL」を区別し、
後者だけ要対応に上げる。1回きりの通信エラーで赤くしないよう、**2回続けて失敗**して
からにしている（連続失敗回数は台帳の `fail_streak`）。

判定規則は `python3 _tools/test_classify.py` で確かめられる（通信しない・12件）。
規則をいじるときは、先にここへ1件足すこと。

出力：`link_report.md`（全件）、`link_report_brief.md`（Issue用・正常分を省く）、
`link_status.json`（前回値の台帳）。

**UAについて。**`chusho.meti.go.jp` はWAFがあり、素性だけのUAには403を返す
（2026-07-31 実測）。ブラウザ相当の文字列にリポジトリURLを足した形にしてある。
アクセス解析のビーコン（goatcounter）は自分でページビューを作ってしまうので叩かない。

### 自動実行

`.github/workflows/linkcheck.yml` が毎週月曜09:00 JSTに回す（手動実行も可）。
要対応が出たら `linkcheck` ラベルのIssueに追記する（毎回新規に立てない）。
結果はリポジトリにコミットされるので、いつ何が変わったかはgit logで追える。

## collect_docs.py — 様式の候補を拾う（下書き作り）

```bash
python3 _tools/collect_docs.py               # 様式未掲載の制度すべて
python3 _tools/collect_docs.py --only tokyo_ # 制度キーで絞る
python3 _tools/collect_docs.py --head        # 候補にHEADを打ち種別・サイズも取る
```

制度の公式ページを開いてPDF・Word・Excelへのリンクを拾い、様式らしい語
（様式／申請書／交付申請／実績報告／記載例…）で並べ替えて
`docs_candidates.md` に出す。`--only` のときは別ファイルに書く。

**出力は掲載可能なリストではない。**同じページに別制度の様式や前年度のファイルが
並んでいることがあり、機械にはどれがどの制度のものか断定できない。
`PROGRAM_DOCS` は「公式サイトで実在を確認できたものだけ」という約束で作ってあるので、
人が公式ページを開いて確かめたものだけを入れること。

2026-07-31 時点の実測：未掲載101制度のうち **83制度で候補が出た**（計625ファイル）。
うち東京都の21制度・133ファイルにHEADを打ったところ **133件すべて HTTP 200**。
残り18制度は公式ページにファイルが無く、様式が別ページか電子申請システム側にある。
